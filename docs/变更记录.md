# 变更记录

> 版本演进史。每条都写明"为什么改"，不只是"改了什么"。

## v6.7（2026-11-05）

- **不良上限 300 → 1,000**。真正解锁它的不是改常量，是 `collect.js` 新增 `runBatched()` 按批并发取贴装明细：795 块板 **77.1s → 3.5s**，端到端 1,000 条约 21 秒。停在 1,000 的理由：再往上板数×贴装行齐涨，逼近 40 秒。
- **★ 修掉参数嗅探导致的 158 秒慢查询**。`windowPanelsQuery` 被复用到不同工单时，缓存的执行计划对这批参数是坏的。同一条 SQL 实测 `158,165ms`，加 `OPTION (MAXDOP 4, RECOMPILE)` 后 `607ms`。案例 168 秒 → 15 秒。
- 粘贴识别默认折叠（`localStorage` 记忆），URL 带参数时自动展开。
- `mapSide` 改规则表按长 key 先比 —— 原来 `AVI` 排在 `AVI-EB` 前面会吃掉它。
- 新增 `tests/run_all.js`（13 套 / 312 断言 / 2 秒）与 `tests/_src.js`（兼容发行包内 `server.js`）。

## v6.6（2026-11-02）

- **按 SN 追溯拆成两条路**：联合追溯（SMT + BE）与仅 BE 单独追溯。
  理由：100 个 SN 走联合路径慢的不是 BE（`beTrace` 只要 149ms），而是 SMT 取对照板（45.8s）。
- 仅 BE 通道 `traceBe()`：不取 SMT 对照，100 SN **2.6 秒**。
- 邻居板取数四级提速：走三列索引、前后方向并行、按 `product|machine` 分组复用（100 个真实 SN 只落 16 组）、空窗短路。联合路径 45.8s → 5～8s。
- 两个前端诚实性修复：只有 1 个 SN 查到记录时不再说"散在不同机台"；占比 1/5,113,326 显示 `<0.01%` 而不是四舍五入成 `0%`（会被读成"一块都没过"）。

## v6.5（2026-10-29）

- **按 SN 追溯的邻居口径从 panel 改成 pcs**。实测 1 块 panel 平均 102 个 pcs、最多 360 —— "前后各 200 块 panel"约等于 20,400 个 pcs，这就是导出大到没法看的原因。
- 两步法取数：先按 panel 取附近几块（1.2～2.4s），再取这些 panel 的全部 pcs（320ms），合计 **3.3 秒**；直接按 pcs 的板号查要 11～14 秒（无索引）。三档可选：30 / 100 / 300 pcs。
- 新增全链路导出（24 列 / 七段事件），只出目标 pcs 的实测值（67,323 行 → 1,141 行）。
- 追溯过程加进度浮层（沿用共性分析的等待浮层）。
- 修 6 个导出 bug，其中两个致命：AOI 行 17 个值对 18 列表头（测量值整体右移一格）；`Number('') === 0` 把"没测"写成"实测 0 / 不超规"。

## v6.4（2026-10-27）

## v6.3（2026-10-25）

- **被动共现分离**（`passive.js`）。用户原话描述的现象：载具某个穴位卡异物 → 那个穴位不良升高、贴那儿的吸嘴不良也升高、同批材料也升高，但吸嘴和材料本身没问题。
  两条不可动的不变量：剔除时**必须连暴露一起减**；**必须不对称**才判被动（否则两个维度互相解释成环）。
  实测逼出一个门槛：不加 `MERGE_LIFT_RATIO=3` 时，233.8× 的穴位会把 1.9× 的机台并进同一簇 → 12 个信号里"被判为被动 0 项"，用户看不出该先动哪个。
- 等待浮层（百分比、六步文案、算完才到 100%）。

## v6.2（2026-10-24）

- **首因 / 传导判读**。工序有先后，前站的问题会让后站也"看起来高"。
- 实现走 `ROW_NUMBER() OVER (PARTITION BY board ORDER BY time, proc)` 找每块板的首个 NG 工序。实测 AVI 首因率 99.61%、VSWR 99.69% → 后段内部跨工序传导只有 0.31%～0.39%。
  结论：用户描述的"置件导致后站高基准"不是 BE 内部传导，而是 SMT→BE 这条边，必须在前后段联动里判。前端加了传导链桥接。
- 踩坑：`proc` 是 T-SQL 保留字，别名必须 `proc_`。

## v6.1（2026-10-21）

- 纯日历天运算（`date_utils.js`，不碰本地时区）；日均分母改用**实际窗口天数**（空白日计 0，原来按有数据的天数算，会虚高）。
- **稳定哈希抽样**（`sampling.js`）：`ORDER BY HASHBYTES('MD5', id)`，同一次查询反复跑结果一致（原来用 `TOP N` 无 ORDER BY，每次取到的板不同，结论会漂）。
- **Holm / BH 跨维度校正**（`stats_adjust.js`）：家族从"单维度内"扩到"全部维度全部候选"，实测 59 候选 / 13 维 → 后测 259 候选。
- **凭据外置**（`config.js`）：env → `~/.config/sinan/` → 包内 `config/` → 未配置则以 `dbConfigured:false` 启动而不崩。原来账号密码写死在源码里，发行包一拷出去等于把凭据一起发出去。

## v6.0（2026-10-20）

给 MES 装刹车。起因是运维问"查询有可能把 SQL 服务器压崩么"，做了一轮压测：
1 人 16.1s / 3 人合计 27.9s / **5 人合计 166.2s** / **8 人成功 4/8，其余 `ECONNRESET`**。

- 语句闸（本机 4 条并发）+ 任务闸（2 个）。
- 时间窗硬上限 31 天。
- `MAXDOP` 8 → 4（实测单条最重查询 DOP8 4169ms / **DOP4 3002ms** —— 降并行度反而更快）。
- 全仓补 `NOLOCK` 52 处；连接池 6 → 4；`appName='PQM-Commonality'` 便于运维识别。
- 人话报错（`humanError()`），不再甩原始 SQL 异常。
- 修一个真 bug：`conn.js` 缓存了失败的 `poolPromise` → VPN 断一次之后永远报连不上。

## v5.2（2026-10-18）

- BE 段共性改用**过站编码**维度。实测 `TRS_Busi_StationTrace.SerialNo` 就是「工位-穴位-轨道」编码：`ZD<机台>VSWR0004-01R` = 机台 / 工序 VSWR / 工位 0004 / 穴位 01 / 轨道 R。
- 新建 `becode.js` 四维解析（机台 / 工位 / 穴位 / 轨道）；BE 载具/钢网维度确认**没有数据源**（`FixtureCode`/`SteelCode` 100% NULL），如实写进边界。
- SN 追溯扩到 18 维（BE 6 / SMT 9 / AOI 1 / SPI 1），并区分"你查的 SN"与"参考板"两种角色。
- 修 `neighbors()` 只查 `TS_AOI_Rear` 的 bug：某些产品 AOI 全在 `TS_AOI_Front` → 对照板恒 0 块，修复后同一案例 0 → 330 块。

## v5.1（2026-10-16）

- **BE 段删掉「不良现象」「不良点位」两个维度**。理由：那是"坏成什么样"（结果），不是"为什么坏"（原因），放进共性分析等于把结论当证据。
- 散落时的结论文案改成「BE 段没有共性，下一步看前后段联动」，而不是硬凑一个。
- SN 导出三修：汇总缺 SN 列、18 列只填 17 个值（列错位）、时间列变成 `Sun Oct 18 2026 …GMT+0800`。

## v5.0（2026-10-15）

- **前后段联动**：BE 不良板号 → 前段面板码映射 → 只在这些面板上做 SMT 共性。
- 对照板口径改了三次才定：按产品模糊取（被量最大的产品占满，两组机型对不上）→ 同工单取（取到"整条流程走满的板"，算出 111× 假倍数）→ **最终：同一时间窗、同一道后段工序判 OK 的板**。倍数回落到 1.2～3 的合理区间。
- 维度 8 项（穴位/机台/载具/钢网/吸嘴/飞达/工序/工站），噪声过滤 `ng≥3` + `sig||lift≥1.3`。
